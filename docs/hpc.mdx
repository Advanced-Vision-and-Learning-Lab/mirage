This guide covers a first GPU run and repeatable model comparisons on a SLURM cluster. Cluster module names, partitions, GPU types, storage paths, and resource limits differ, so check your center's instructions and edit `slurm/demo.slurm` for local requirements.

## What you need before submitting

- A clone of Mirage on storage visible to the compute nodes.
- A Python environment with the pinned packages in `requirements.txt`.
- Dataset annotations and images arranged as described in [Datasets](/datasets).
- The model weights already available in the Hugging Face cache or on cluster storage. Nodes without internet access cannot download weights during the job.
- A GPU allocation sized for the selected checkpoint and evaluation. The sample SLURM request is a starting point, not a guarantee that a model fits.

The repository exposes `paligemma`, `qwen2vl`, `gemma4-e4b`, `gemma4-12b`, `ministral3-8b`, `ministral3-14b`, and `aya-vision-8b` to `demo.py`. See [Metrics and models](/metrics-and-models) for checkpoint defaults and overrides. The Gemma 4, Ministral 3, and Aya Vision keys were tested on A100 40 GB GPUs with `transformers==5.19.0`, `torch==2.9.1` (CUDA 12.8), and `mistral-common==1.12.0`, as pinned in `requirements.txt`. DeepSeek-VL is not currently implemented as a Mirage model backend, so it cannot be selected with `--model` or `MIRAGE_VL_MODEL`.

## Clone and prepare the environment

Clone the repository to a project or work directory that compute nodes can read:

```bash
git clone https://github.com/Advanced-Vision-and-Learning-Lab/mirage.git
cd mirage
```

Load the Python and CUDA modules required by your center, then create the environment. Match the PyTorch installation to the cluster's supported CUDA setup. The pinned versions are in `requirements.txt`.

```bash
module load Python/3.11
module load CUDA/12.4
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

Module names and versions above are examples. If the cluster provides a supported PyTorch environment, follow its installation instructions and install any remaining project requirements into that environment.

Check that the environment can see the GPU and that the CLI is available:

```bash
python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'CPU')"
python demo.py --help
```

## Stage data and model weights

By default, Mirage expects COCO validation data under `datasets/coco/` or Visual Genome data under `datasets/visual_genome/`. Large files are intentionally excluded from Git. If your files live elsewhere, pass `--annotations` and `--images` to `demo.py`; for the sample SLURM script, edit the command to add those options or place data at the default paths.

Set a persistent Hugging Face cache path on storage visible to compute nodes. If outbound downloads are disabled, download or stage the model snapshot on a login or transfer node first, then point the corresponding model path variable to that snapshot.

```bash
export MIRAGE_HF_HOME=/path/to/shared/huggingface
export MIRAGE_QWEN_MODEL_PATH=/path/to/models/Qwen2-VL-2B-Instruct
```

For PaliGemma, use `MIRAGE_PALIGEMMA_MODEL_PATH`. The default is a Hugging Face model identifier, which requires the model files to be cached or reachable. Some gated model repositories also require access approval and Hugging Face authentication before downloading.

## Submit a small Qwen2-VL run

The sample job runs five COCO images by default. Set these variables before submitting to request a small Qwen2-VL CHAIR run:

```bash
export MIRAGE_DATASET=coco
export MIRAGE_METRIC=chair
export MIRAGE_VL_MODEL=qwen2vl
export MIRAGE_SAMPLES=5
export MIRAGE_OUTPUT=results/qwen-coco-chair.json
export MIRAGE_CACHE_DIR=/path/to/scratch/mirage-cache/qwen-coco-chair
sbatch slurm/demo.slurm
```

For Visual Genome, set `MIRAGE_DATASET=visual_genome`. To run another supported metric, set `MIRAGE_METRIC` to `pope`, `rope`, `throne`, or `faithscore` as well as `chair`. FaithScore has extra requirements; see [Metrics and models](/metrics-and-models). NOPE uses a separate input flow documented in [Running evaluations](/running-evaluations).

The job writes standard output and errors to `mirage_<job-id>.out` and `mirage_<job-id>.err`, and the evaluation result to the path passed through `MIRAGE_OUTPUT`. Check the generated JSON and job logs after completion. Keep result paths unique across jobs to avoid overwriting earlier runs.

## Compare model configurations

Run separate jobs for each supported model and metric combination, changing `MIRAGE_VL_MODEL`, the model path variable, and the output path each time. For example, to compare PaliGemma and Qwen2-VL on the same data and metric:

```bash
export MIRAGE_DATASET=coco
export MIRAGE_METRIC=chair
export MIRAGE_SAMPLES=100

export MIRAGE_VL_MODEL=paligemma
export MIRAGE_OUTPUT=results/paligemma-coco-chair.json
export MIRAGE_CACHE_DIR=/path/to/scratch/mirage-cache/paligemma-coco-chair
sbatch slurm/demo.slurm

export MIRAGE_VL_MODEL=qwen2vl
export MIRAGE_OUTPUT=results/qwen-coco-chair.json
export MIRAGE_CACHE_DIR=/path/to/scratch/mirage-cache/qwen-coco-chair
sbatch slurm/demo.slurm
```

For an initial comparison, keep the dataset, metric, sample count, and other evaluation options the same. The current built-in model keys are listed in [Metrics and models](/metrics-and-models).

Each job can use a distinct `MIRAGE_CACHE_DIR`. Cache keys include model identity, prompt, image, and generation settings, so cached responses are reused only when those inputs match. SQLite caches work best when each concurrent job writes to its own database on storage suitable for SQLite. A shared cache can save repeated inference across sequential runs, but avoid multiple active writers to the same cache file unless your filesystem and workload have been validated for that use.

## Adapt the sample job

Before using `slurm/demo.slurm` for a full evaluation, edit its `#SBATCH` resource requests and module setup for your cluster. The example requests one GPU, four CPUs, 32 GB of host memory, and four hours. Resource needs depend on the model, metric, image resolution, and sample count. Start with a small pilot and scale the allocation after inspecting GPU memory and run time.

For custom dataset paths, extra model arguments, partitions, account codes, or module commands, edit the script's `python demo.py` command and `#SBATCH` block. Then submit it from the Mirage repository root with `sbatch slurm/demo.slurm`.

## SLURM cells

`slurm/eval_cell.slurm` runs one model, dataset, and metric cell on a SLURM cluster. It requests one A100 40 GB GPU on the `gpu` partition, loads `GCC/13.3.0 Python/3.12.3 CUDA/12.8.0`, activates `venv/` in the repository root, and runs offline (`HF_HUB_OFFLINE=1`), so download weights on a login node first. It reads `MIRAGE_VL_MODEL`, `MIRAGE_DATASET`, `MIRAGE_METRIC`, `MIRAGE_SAMPLES` (default 500), `MIRAGE_CACHE_DIR` (required), and optional `MIRAGE_EXTRA_ARGS`, `MIRAGE_OUTPUT` (default `results/<job name>_<job id>.json`), and `MIRAGE_HF_HOME` (default `huggingface/` in the repository root, which must already hold the weights). The walltime and job name come from `sbatch` options. Set the model's `MIRAGE_*_MODEL_PATH` to a Hugging Face snapshot directory (`.../snapshots/<sha>`) so cache keys record the model revision; with a bare model id the revision is keyed as `unpinned`, and caches written with a snapshot path will not be reused. Download NLTK data (`python -m nltk.downloader stopwords punkt_tab wordnet`) on a login node, because compute nodes are offline.

```bash
mkdir -p slurm/logs
MIRAGE_VL_MODEL=qwen2vl MIRAGE_DATASET=coco MIRAGE_METRIC=chair MIRAGE_SAMPLES=500 \
MIRAGE_CACHE_DIR=$PWD/cache/qwen2vl_coco_captions \
    sbatch --time=01:30:00 --job-name=qwen2vl_coco_chair slurm/eval_cell.slurm
```

Give each cell its own cache directory. To score THRONE on the same captions without regenerating them, submit a second cell with the captions cell's `MIRAGE_CACHE_DIR`, `--dependency=afterok:<captions job id>`, and `MIRAGE_EXTRA_ARGS="--cache-only --throne-evaluator <path> --throne-distractor-ratio 38"`. The THRONE evaluator answers are cached in `$MIRAGE_CACHE_DIR/evaluator.sqlite`. To replay a fully cached cell on CPU, add `--partition=short --gres=none`.
